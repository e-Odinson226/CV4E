# Session hand-off, 2026-10-08

A summary of this session, for picking the work back up in a new one. This is not a vault

## The big change this session: what the paper reports on

The project's result will now be measured on two benchmarks with gaze, not on an internal
measure alone:

- **HD-EPIC's gaze interaction anticipation.** 1,000 five-choice questions, chance 20%, best
  published 27.5% (no training on HD-EPIC — it has no training split; every published number
  comes from a model that never saw HD-EPIC data).
- **EGTEA Gaze+ action anticipation.** 28 hours of cooking, three official train/test splits,
  2D gaze, established baselines (RULSTM, AVT, SAGE).

A later edit (`3-method.md`, see "What Erfan edited" below) sharpened this: because HD-EPIC has
no training split, a model trained on our own P01–P07/P08–P09 division can never be placed next
to a published HD-EPIC number. The plan is now: train and evaluate on EGTEA's official split
first (the number that goes in a comparison table), then run that same trained model on HD-EPIC
with no further training, as a secondary zero-shot check, never the main result.

### A bug found and fixed this session

`score()` in `gaze_forms.py` decided what signal to feed a model with
`form in ("none", "before fine-tuning")` — an exact string match. Once `form_of()` started
appending `" l1"`/`" full"` suffixes, a model named `"none l1"` or `"none l1 full"` no longer
matched, so it silently got fed real gaze and hand instead of the masked input it was trained
on. This inflated its "mse"/"l1" column (which should equal "mse_hide"/"l1_hide" for a model
that never saw real signals) and made it look like gaze hurt it badly.

Fixed with a `base_form()` helper that strips the suffixes before the comparison, in both the
`given = …` line and the `key = "sig_next" if … else "sig"` line (same class of bug, same fix).
Covered by two new checks in `tests/test_finetune.py`. The two already-computed, wrong score
caches (`results/test10/scores/none_l1_s0.npz`, `none_l1full_s0.npz`) were deleted so they get
recomputed. **`results/test10/gaze_forms.csv` as it stands right now still has the old, wrong
numbers for `none l1` and `none l1 full`** — they will be correct once the queue's `eval all`
step runs (end of the queue, see below). Until then, any comparison that uses `none l1` or
`none l1 full` is not trustworthy; everything else (`pe l1`, `pe l1 full`, the references, all
of Test 9's pooled forms) is unaffected and fine to use.

## Test 10: running now

Purpose: does training with L1 (the pretraining's own loss) instead of MSE change anything, and
does training the whole predictor (not just the last 6 blocks) change anything — for prediction
quality in general, and for how much gaze specifically helps.

Queue: `checkpoints/test10/queue.sh`, driven by `checkpoints/test10/todo.txt`, logs to
`checkpoints/test10/queue.log`. It is running detached (`setsid nohup`), so it survives a
session ending. Four arms, three seeds each: `pe l1`, `none l1` (signal dropout 1.0, same as
`ego_sd1p0`), `pe l1 full`, `none l1 full`. Recipe otherwise identical to Test 9's: 3 epochs,
P01–P07, 30 clips/recording, batch 16, no warmup.

**Status as of 15:35:** seed 0 of all four arms finished, plus one `eval first` pass (whose
`none`-family numbers are the stale/wrong ones above). Currently training `none_l1_s1` (seed 1).
Six more training runs queued after it, then `eval all`. At about 40 minutes per run, the whole
queue should finish roughly 4–5 hours from 15:35, i.e. around 19:30–20:30 today. GPU: 32/46 GB,
100% util, stable. Disk: 44 GB free on `/mnt/data` (98% full) — a real constraint if V-JEPA 2.1
or EGTEA get added (EGTEA alone is about 22 GB).

**What the one finished full fine-tune (`pe_l1full_s0`) shows, on its own, one seed:** training
the whole predictor (not just the last 6 blocks) predicts noticeably better overall — it beats a
simple blend-of-past-frames baseline by 0.024 error, about twice the margin the last-6-blocks
version gets (0.012). But the measured extra contribution of gaze itself was, if anything, a
touch smaller with the whole predictor trained (0.0002–0.0004) than with just the last 6 blocks
(0.0006–0.0007) — both tiny, and smaller than the seed-to-seed spread Test 9 found (0.0006–
0.0014), so this is not yet a real difference, just the one data point so far. The real test —
`pe l1 full` against its matched no-gaze twin `none l1 full` — needs the bug above fixed in the
scores, which happens at `eval all`.

**To check progress in a new session:** `tail checkpoints/test10/queue.log`,
`cat results/test10/gaze_forms.csv` (once `eval all` has run), `nvidia-smi`.

## What Erfan edited this session (not touched, explained only)

Three documents, read and explained in full but never modified:

- **`3-method.md`**, "Alternative Datasets for Official Evaluation." Lists EGTEA Gaze+,
  Ego-Exo4D, Ego4D STA, and VEDB as candidates, with a recommendation to train on EGTEA's
  official split first. One figure worth double-checking: it gives Ego-Exo4D as "1,400+ hours";
  earlier research in this project found closer to 88 hours of actual egocentric (Aria)
  footage, with the larger figure likely counting all the exocentric GoPro views together too.
- **`5-discussion.md`**, "Weak points of the design." Two of the five named weak points
  ("Gaze cannot point," "The signals describe the present") were rewritten as "1. The Spatial
  Mismatch" and "2. The Temporal Mismatch," with "Proposed Solutions" under each, and the third
  named weak point ("Short horizon, coarse measure") no longer has its own heading — its content
  is folded into "Temporal Mismatch." This is a factual note, not a request to fix it:
  `CLAUDE.md`, which Erfan wrote, says to keep exactly those five names and add no others. Worth
  a conscious decision, not raised again unless asked.
- **`docs/7-predictor-redesigns.md`** (new file, outside the 1–6 chapter numbering, not linked
  from anything yet). Four ways to make gaze a real spatial signal inside the predictor's
  attention, instead of a token that can't point: (1) add a Gaussian bias centered on the gaze
  point directly to the attention scores before softmax, (2) give the gaze token a position
  encoding matching the image patches' own, so they naturally attend to each other, (3) scale up
  the patch features near the gaze point (FiLM-style) so they dominate attention by sheer
  magnitude, (4) replace attention near the gaze point with deformable (sparse, learned-offset)
  attention, discarding the pretrained weights entirely.

My read, after comparing these against Test 9's actual results: option 1 is worth testing
seriously, because it does not have the same problem that sank Test 9's `rope` form (moving a
token the frozen blocks already relied on heavily) — it never touches the gaze token's identity
or position, only nudges ordinary patch-to-patch attention. Options 3 and 4 I'd set aside:
3 conflates "loud" with "important" and risks shifting a distribution the frozen blocks never
saw; 4 throws away the pretraining the whole project leans on. I'd build option 1 and the
already-planned Test 11 design (gaze added to token content, with a learned scale starting at
0) side by side, since Test 9's evidence doesn't clearly favour one channel (content vs.
attention) over the other.
